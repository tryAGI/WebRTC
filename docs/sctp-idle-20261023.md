# Quiescent SCTP scheduling and measured allocation budgets

Baseline measurement source: `9f3f7362c575aaca1504ee9653efdb8e0180d9cf`.
The new idle-sctp suite compares data channels disabled, SCTP associated without
DCEP, and a warmed bidirectional open channel. AES-256-GCM, one/three pairs,
tracing off/on, three two-second samples; CI runs three fresh processes per
native platform. Final SCTP occupancy must be zero. Source and configuration
metadata remain in each artifact. A preliminary local working-tree cohort
observed ~230 KB/s process managed allocation for one idle associated pair and
~710 KB/s for three, versus ~45 KB/s without SCTP. That local source metadata is
unverified; exact-source hosted baselines are the authoritative comparison.

The runtime stops periodic ticks only when an established association has no
pending handshake/control flight, outbound data, FORWARD-TSN, reset, SACK/control
output or shutdown. Existing 10 ms maintenance remains for every nonquiescent
state; no retransmission, partial-reliability, reset or shutdown deadline changes.
Incoming authenticated records and external API calls continue to wake the pump.
A queued old tick may still be delivered once when the timer period changes.
The bounded MaintenanceTicks diagnostic counts timer iterations, not kernel
wakeups. It remains available after disposal with other SCTP counters.

Local solution build passed with zero compiler/analyzer warnings/errors. The
new idle regression proves stable ticks while quiescent, then prompt send,
channel reset/reopening and disposal. All 43 local SCTP-filtered integration
cases passed (including the selected case); independent peer/native gates and
matched benchmark acceptance are recorded separately when complete.

Longer retention controls use fresh processes for empty harness, identity-only,
audio-only peers and open-channel peers, with tracing off/on for peer modes.
Four warmup waves precede 24 measured two-pair waves, each with two seconds live
idle, synthetic bidirectional media, deterministic ownership checks and disposal.
Weak-reference collection, heap/GC committed/fragmented bytes, RSS and available
private bytes/handles are retained. A finite plateau does not prove native leak
freedom, nor does RSS minus GC committed measure precise native allocations.

Allocation budgets will be calibrated from repeated matched-platform samples,
retaining separate training and holdout observations. No arbitrary shared-runner
wall-clock gate or auto-growing warning baseline is introduced. Synchronous
crypto/parser contracts retain an exact zero-byte budget; new raw total-byte
columns prevent decimal per-operation formatting from hiding a small regression.

## Baseline and diagnostic controls

[Before matrix](https://github.com/tryAGI/WebRTC/actions/runs/40012542666)
passed all four platforms. One-pair/no-trace medians across three fresh processes
were 175–243 KB/s with an open SCTP channel, versus 43–56 KB/s without SCTP.
All 70 raw exact-zero crypto/parser samples per platform also passed the new
checker (280 exact measurements total), rather than relying on rounded output.

The preliminary local post-change cohort observed associated 231,941.76 ->
46,146.92 bytes/s and open-channel 238,286.70 -> 51,853.31 bytes/s. Off remained
50,578.04 -> 50,428.97. These local harness sources were working-tree unverified;
matched committed-source CI measurements remain the acceptance comparison.

A separate instrumented macOS 27.0.1/.NET 10.0.9 open-channel, tracing-on cohort
used vmmap on only the owned benchmark process, at approximately 15 and 45 seconds.
Both native snapshots succeeded. Completed-wave observations were wave 2 and 16:
managed committed bytes stayed at 6,389,760; managed heap ~482,648 -> 546,352;
RSS 90,193,920 -> 101,154,816 bytes. Malloc-zone resident pages grew ~14.8 ->
22.7 MiB, while reported live malloc bytes decreased ~7,941 -> 4,211 KiB and
free/fragment space grew ~7,243 KiB -> 18.6 MiB. Physical footprint grew
60.3 -> 70.8 MiB, a separate OS accounting scope from RSS. This attributes part
of the observed growth to allocator page retention/fragmentation in this cohort;
it does not prove that all memory growth is harmless or identify every allocation
owner. All peer weak references were collectible. The final three RSS waves were
100,646,912 / 100,646,912 / 100,548,608 bytes. The profiler can perturb the process;
these snapshots are diagnostic controls, not the uninstrumented CI benchmark.
An earlier process ended before its second manual snapshot; it is not presented
as a paired observation. No other process was profiled and no allocator/runtime
configuration was changed to force a lower RSS.

The real local benchmark allocation control injected one escaping 256-byte array
per crypto sample, measured 280 bytes including object overhead, and the exact
validator rejected all 42 samples. All 70 normal samples remained zero. Thirty
Python checks (including the existing package tests) passed; new cases cover
rounded-small-allocation masking, missing/duplicate/undrained samples, nonfinite
metrics, holdout rejection, runtime drift and refusing automatic ceiling growth.

## Committed-source comparison and reviewed budgets

[After matrix](https://github.com/tryAGI/WebRTC/actions/runs/40013111120),
source `a20b2ad5b11100e606f917ba7e586944977d8cc2`, passed on all four platforms,
including the complete longer memory controls. All nine independent validation
lanes passed in [40013111233](https://github.com/tryAGI/WebRTC/actions/runs/40013111233)
(Pion x64/arm64, Chromium, protocol/network and NativeAOT). Publication is separate.
Three fresh-process medians per platform, AES-256-GCM, one open-channel pair,
no tracing, same .NET 10.0.13/platform/runner class in distinct jobs:

| Platform | Before managed bytes/s | After managed bytes/s | Before threadpool items/s | After threadpool items/s |
|---|---:|---:|---:|---:|
| macOS arm64 | 175199.57 | 37502.78 | 162.97 | 22.43 |
| Linux arm64 | 237529.51 | 53294.62 | 247.00 | 41.00 |
| Linux x64 | 242565.46 | 51197.70 | 249.50 | 41.99 |
| Windows x64 | 202240.93 | 48804.63 | 196.50 | 28.50 |

Observed reductions: 76–79% process managed allocation and 83–86% completed
threadpool work. These are scoped observations, not kernel wakeups/energy or
production latency guarantees. The complete transport remains nonzero.

Every disposed peer in all fresh-process controls was collectible. macOS
open-channel/tracing-on post-change RSS was 87,080,960 -> 95,338,496 bytes;
managed committed stayed 6,389,760 and the last three RSS samples were
95,322,112 / 95,338,496 / 95,338,496. Linux GC committed/RSS still evolved and
Windows RSS decreased. Compare OS scopes and controls; no leak-freedom or native
memory reduction claim is derived from the lower managed allocation rate.

`specs/performance-budgets.json` records four reviewed .NET 10.0.13 cohorts from
this after matrix. Processes 1/2 train each ceiling; independent process 3 passed
every holdout. All after artifacts passed strict exact-zero and idle gates;
the old polling baseline was rejected by the resulting allocation budgets on
all four platforms, a real regression control. Future validation never updates
limits and unreviewed runtime/platform cohorts fail for review. CI wiring and a
real per-sample allocation positive control are verified separately after the
budget commit. The normal performance workflow retains full longer controls by
default; `long_retention=false` is available when verifying benchmark gates after
the runtime's full before/after memory cohorts have already passed. It does not
skip ordinary protocol or independent-peer validation.
