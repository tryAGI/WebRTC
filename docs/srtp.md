# SRTP/SRTCP key contexts

`SrtpContext` protects RTP media and RTCP control packets using .NET cryptography.
It is a directional key generation, not a DTLS connection or key negotiation API.
Its presence does not establish a usable WebRTC peer or provider/media E2E.

## Supported wire profiles

| DTLS-SRTP identifier | Profile | Master key/salt | RTP/RTCP expansion |
|---|---|---|---|
| 0x0001 | AES-128-CM / HMAC-SHA1-80 | 16 / 14 bytes | 10 / 14 bytes |
| 0x0007 | AEAD AES-128-GCM | 16 / 12 bytes | 16 / 20 bytes |
| 0x0008 | AEAD AES-256-GCM | 32 / 12 bytes | 16 / 20 bytes |

The session key derivation rate is zero, as used by DTLS-SRTP. RTP and RTCP use
separate derived keys/salts. AES-CM is built from the platform AES primitive;
HMAC-SHA1 is retained only for the negotiated legacy protocol profile, not for
signatures or a new general-purpose cryptographic design. GCM uses `AesGcm` with
its complete 16-byte tag. Authentication comparisons for the HMAC profile use
fixed-time comparison. MKI, truncated 32-bit RTP tags, Cryptex and encrypted header
extensions are not implemented.

## Ownership and bounds

Use independent key/salt material for sending and receiving, derived from an
authenticated DTLS exporter. This exporter/handshake is not yet implemented.
Never recreate a send context with previously used keys, reset indices, reuse an
SSRC's sequence space or evict its state within the same key generation. Re-key
with fresh material before limits are reached. Disposal closes the context and
disposes platform cryptographic handles; intermediate keys/plaintext are cleared.
The caller owns and must clear its original key buffers.

Methods serialize access internally. Each direction maintains at most 32 RTP and
32 RTCP SSRCs, with no eviction. Plaintext datagrams are limited to 4096 bytes.
Only authenticated valid inbound packets admit a new source or update counters.
The replay window contains 64 indices per source. Receive-side ROC estimation
handles reordering across sequence rollover; ambiguous jumps beyond half the
sequence space require a new negotiated generation. Counters never wrap at their
key limits: at most 2^48 RTP and 2^31 RTCP operations across all sources per context,
with a 48-bit RTP index and a 31-bit RTCP index.

Send-side RTP indices must strictly increase. Retransmit saved ciphertext for an
identical original packet, or use RTX with its own SSRC/sequence space. Do not
encrypt a different payload under an existing index. SRTCP sends encrypted E=1
packets; it receives both authenticated encrypted E=1 and authentication-only E=0.
The AEAD SRTCP tag precedes the explicit index, unlike the HMAC profile.

Use separate input/output buffers. `false` from an unprotect operation leaves the
destination and authentication/replay state untouched; temporary plaintext is
released only after authentication and structural validation. Packet type-specific
RTCP body semantics belong to a future RTCP parser; this layer validates compound
packet framing, lengths and final padding. RTP header extensions remain opaque
authenticated header bytes at this layer.

## Validation scope

The default suite includes reproducible synthetic known-answer vectors generated by
the pinned independent peer, including authentication-only SRTCP. Reproduce them with
`docker run --rm --entrypoint pion-peer tryagi-webrtc-interop --srtp-vectors`.
It covers all profiles, extensions/CSRC/padding/empty payloads,
every-byte mutation and truncation, wrong keys, rollover/reordering, duplicate and
expired replay indices, unauthenticated source flooding, buffer overlap/capacity,
source bounds, disposal/direction and deterministic hostile inputs. Integration
tests send encrypted RTP over real local nominated UDP pairs with synthetic keys.

The isolated Pion peer independently encrypts/decrypts the same synthetic packet
series, including RTP rollover, reordered delivery and E=0 SRTCP. Exact ciphertext
comparison checks key derivation, nonce, authenticated header and trailer layout.
The NativeAOT smoke executes all three profiles and encrypted local ICE datagrams.
None of these fixtures contains provider credentials or negotiates DTLS keys.
